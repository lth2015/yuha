# YUHA · 空气作曲 — 第一阶段规格（触控 MVP）

> 2026-10-25。状态：待实施。本文只覆盖第一阶段；第二阶段（可选摄像头）与
> 第三阶段（接入正式生成）各自另写规格。
>
> 一句话：**不必懂音乐，让感觉先有声音。** 用户用身体表达一种音乐情绪，
> 每个动作都得到即时、连续、优美的回应；30 秒后得到一份属于自己的
> 音乐情绪草图。

## Problem Statement

YUHA 首页请用户「描述一种感觉」。很多人有感觉却说不出来：他们不懂旋律、
节奏、和声，也找不到词。文字是 YUHA 现在唯一的入口，于是这部分人在第一步
就停下了。

同时，我们还不知道「用动作表达情绪」这件事本身是否成立：第一次触碰后能不能
立刻听到好听的声音、人是否愿意自己探索下去、玩完后是否真的想把它变成一首歌。
在这三点被验证之前，把它接进正式生成流程、首页或 iOS App 都是过早的投入。

## Solution

一个独立的 Web 实验页面：无需登录、无需 Credit、不调用任何后端。

1. **触碰，声音诞生。** 没有教程。手指落下的一瞬间就有声音，光随手指流动。
2. **自由探索 20～30 秒。** 手向上，音区升高、声音变亮；向下，变得深沉；
   移动越快，音符越密；手指停留，声场慢慢打开；两指分开，和声层次增加。
   无论怎么动都不会「弹错」，因为背后有一条自己向前走的和声进行，
   用户只是在其中选择。
3. **松开，聆听自己的草图。** 回放刚才的演奏，与刚才听到的完全一致。
   可以重来，也可以把草图作为链接分享，打开链接的人听到同一段演奏。
4. **「让它成为一首歌」。** 第一阶段不生成：展示一张「你的草图」参数卡
   （情绪、速度、能量，用文字说出来），并给出前往 yuha.studio 的链接。
   这张卡同时检验了第三阶段要做的翻译是否说得通。

默认输入是触控（一根手指即可），iPhone、iPad、桌面浏览器均可体验；不请求
摄像头。

## User Stories

**第一次触碰**

1. 作为第一次打开页面的访客，我希望不需要登录、注册或看教程，以便立刻开始。
2. 作为访客，我希望第一次触碰屏幕的瞬间就听到声音，以便知道「是我让它响的」。
3. 作为 iPhone 用户，我希望即使静音键开着也能听到声音（或者被清楚告知为什么听不到），以便第一次体验不会在沉默中失败。
4. 作为访客，我希望手指落下时立刻看到光的回应，以便在声音之外也感到被回应。
5. 作为访客，我希望第一个声音就是好听的，以便愿意再碰第二次。
6. 作为手机用户，我希望在页面上滑动时页面本身不滚动、不缩放、不触发系统手势，以便专心演奏。
7. 作为桌面用户，我希望用鼠标或触控板拖动也能演奏，以便不需要触屏设备。
8. 作为网络较慢的访客，我希望页面在加载完成前清楚地表明「还没准备好」，以便不会在无声中误以为坏了。

**探索**

9. 作为访客，我希望手向上移动时声音升高、变亮，以便不用记规则就能理解。
10. 作为访客，我希望手向下移动时声音变低、变深沉，以便表达低落或平静。
11. 作为访客，我希望移动越快音符越密，以便表达急切或兴奋。
12. 作为访客，我希望手指停住时音乐不会变成噪声，而是安静地延续，以便停下来感受。
13. 作为访客，我希望手指停留越久声场越开阔、音色越丰富，以便表达「展开」。
14. 作为访客，我希望两根手指分开时和声变得更厚、空间更大，以便表达辽阔。
15. 作为访客，我希望无论怎么乱动都不会出现刺耳的错音，以便放心探索。
16. 作为访客，我希望声音随动作连续变化而不是一档一档跳变，以便感觉流畅。
17. 作为访客，我希望手指离开后声音自然消散而不是戛然而止，以便有呼吸感。
18. 作为访客，我希望每次进入时音乐的底色（和声与音色）可以不同，以便重来时仍有新鲜感。
19. 作为访客，我希望看到一个不打扰的提示，告诉我这次演奏还剩多久，以便心里有数。
20. 作为访客，我希望可以提前结束，以便不必等满 30 秒。

**回放与重来**

21. 作为访客，我希望结束后立刻听到自己刚才的演奏，以便聆听我创造的东西。
22. 作为访客，我希望回放与我演奏时听到的一模一样，以便相信「这是我做的」。
23. 作为访客，我希望回放时画面重现我当时的光迹，以便看见自己的动作。
24. 作为访客，我希望一键重新开始，以便再试一种情绪。

**分享**

25. 作为访客，我希望把我的草图复制成一个链接，以便发给朋友。
26. 作为收到链接的人，我希望打开后点一下就能听到同一段演奏，以便感受朋友的情绪。
27. 作为收到链接的人，我希望听完后可以自己也来一段，以便从听众变成创造者。
28. 作为分享者，我希望链接本身不把我的任何信息发给服务器，以便放心分享。
29. 作为收到损坏或过期格式链接的人，我希望看到友好的提示并直接开始自己的演奏，以便不被报错卡住。

**成为一首歌**

30. 作为访客，我希望看到我的草图被说成文字（例如「明亮、开阔、中速流动」），以便确认它理解了我的感觉。
31. 作为访客，我希望从这里前往 YUHA 生成完整歌曲，以便把草图变成作品。
32. 作为访客，我希望被明确告知这个实验页面本身不收费、不消耗 Credit，以便没有顾虑。

**语言、无障碍与隐私**

33. 作为日语、中文或英语用户，我希望页面使用我的语言，以便看懂仅有的几句文字。
34. 作为开启了「减少动态效果」的用户，我希望光效收敛，以便不感到不适。
35. 作为读屏用户，我希望页面告诉我这是一个声音实验以及如何开始，以便我能参与。
36. 作为注重隐私的访客，我希望页面不请求摄像头、麦克风或位置，不设置 Cookie，不发送统计，以便安心使用。

**运营与验证**

37. 作为主持可用性测试的人，我希望用一个调试开关看到「触碰到发声」的实测延迟，以便记录第一项验证。
38. 作为主持人，我希望有一份固定的观察记录表和通过标准，以便几轮测试的结论可以比较。
39. 作为 YUHA 的维护者，我希望这个实验对 Web 正式站和 iOS App 零影响，以便它可以随时被删除或重做。
40. 作为 Wonderful World 的开发者，我希望拿到一份与平台无关的输入信号约定，以便两个产品各自实现、日后需要时再合并。

## Implementation Decisions

**位置与边界**

- 新建一个独立的工作区应用 `@yuha/air`（Vite + TypeScript，无 UI 框架：只有
  一个画布和三四个按钮，首屏体积直接决定「3 秒」）。
- 它不依赖 api、db、providers，不发起任何网络请求（静态资源加载除外）。
  唯一的工作区依赖是对 `@yuha/contracts` 的**仅类型**引用，用于让参数卡的
  取值与正式生成的 `Mood` / `TempoHint` 保持同一套词汇。
- `apps/web` 不引用它，它也不进入 Capacitor 打包的 iOS App。这是不影响
  iOS 里程碑的结构性保证，而不仅是约定。
- 生产托管（例如 yuha.studio 下的某个路径）属于运营方决定，单列一张票，
  不阻塞第一阶段。可用性测试用预览构建即可。若日后挂到正式域名，须按
  CLAUDE.md 的教训，用「只有本应用能正确回答的请求」检查路径真的被路由到，
  而不是被 SPA 兜底页以 200 吞掉。

**模块与唯一测试缝**

整个实验分成一个纯逻辑核心与几个薄适配层：

- **草图引擎（纯逻辑，唯一的测试缝）**：输入帧进、音乐事件出。包含演奏器、
  预设、草图编解码、参数描述四个部分，不接触 DOM、Web Audio、时钟或
  `Math.random`。所有时间来自帧的时间戳，所有随机来自传入的种子。
- **输入适配层**：把 Pointer Events 变成标准输入帧。第二阶段的摄像头适配层
  产出同一种帧，引擎无需改动。
- **声音适配层**：把音乐事件交给合成器（Tone.js，锁定确切版本，在页面空闲时
  预加载，确保第一次触碰时已就绪）。
- **画面适配层**：把同一串音乐事件和输入帧画成光。光效只由真实事件驱动，
  不用随机数伪造节拍（与 `apps/web` 现有原则一致）。

**输入帧：与 Wonderful World 共享的约定**

这是两个产品之间唯一共享的东西，以文档形式共享，不以代码包共享：

```ts
// 约定的形状（文档级契约，两边各自实现）
type GestureFrame = {
  t: number;              // 毫秒，单调递增，从本次演奏开始计
  active: boolean;        // 是否有手指/手在「按下」
  x: number;              // 0..1，左→右
  y: number;              // 0..1，下→上（向上为大，符合「抬高」的直觉）
  speed: number;          // 0..1，已平滑、已归一化的移动速度
  openness: number;       // 0..1，「张开」程度
  spread: number | null;  // 0..1，两点（两指/两手）距离；单点时为 null
  confidence: number;     // 0..1，触控恒为 1；摄像头为识别可信度
  source: 'touch' | 'pointer' | 'camera';
};
```

- 采样：输入适配层按动画帧产出；录制与分享按 20 Hz 下采样。
- 触控下的 `openness`：单指没有「张开手掌」的动作，因此定义为**停留越久越
  张开**（按下后约 2 秒内从 0 升到 1，移动时缓慢回落，抬起清零）。这是暂定
  映射，以可用性测试结果调参。
- 触控下的 `spread`：两指之间的距离。

**音乐映射（连续、单调、无需记忆）**

| 输入 | 音乐反馈 |
| --- | --- |
| `y` 升高 | 音区升高，滤波器打开，声音变亮 |
| `y` 降低 | 音区降低，声音变深沉 |
| `speed` 增加 | 音符密度增加（每拍 0 → 最多 4 个），**速度（BPM）不变** |
| `openness` 增加 | 声场变宽，混响与音色层增加 |
| `spread` 增加 | 同时发声的和声层从 1 增加到 3 |
| `active` 变为 false | 音符停止新生，已有声音自然衰减 |

- 速度只改变密度、不改变 BPM，是保证「乱动也好听」的关键约束之一。
- 所有映射都经过平滑，不出现档位跳变。

**音乐性：结构保证，而不是随机**

- **预设**：BPM、调性、和弦进行（每个和弦是一组音级）、允许的音阶（以五声
  为主）、音色组合。首版 4～5 套，每次进入时由种子选择一套。
- **和声时钟**：和弦按小节自行推进，与用户动作无关。用户只决定「在当前和弦
  允许的音里选哪一个、多密、多宽」。
- **量化**：音符落在十六分音符网格上；强拍只取和弦音，弱拍可取音阶音。
- **静止与空闲**：手指停住时只延续或轻柔重复，不产生密集音符；没有输入时
  不产生任何音符。
- 参照与边界：Brian Eno 的 *Bloom* 走的是「触碰生成受约束旋律」的路。我们用它
  校准「好听」的下限，在视觉语言与交互结构上有意与之区分。

**一次演奏的流程**

- 首次触碰即开始，最长 30 秒（不打扰的进度环），可点「完成」提前结束；
  不足约 5 秒的演奏不进入回放，直接允许重来。
- 结束后进入回放页：回放、重来、复制链接、「让它成为一首歌」。

**草图与分享链接**

- 草图 = 版本号 + 预设 id + 种子 + 20 Hz 量化输入帧。**录的是动作，不是
  音频**；回放就是把草图重新喂给同一个引擎，所以与现场演奏逐事件一致。
- 编码为 base64url 放在链接的 `#` 片段里（浏览器不把片段发给服务器）；
  30 秒最坏情况不超过 4 KB。
- 解码失败、版本不认识、数据越界时返回「无草图」，页面友好提示并进入新的
  演奏，不抛错。
- 打开分享链接后需要一次点击才开始播放（浏览器要求用户手势才能出声）。

**参数卡（第三阶段翻译的预演）**

- 由草图确定性地计算：`mood`（取值属于 contracts 的 `Mood`）、`tempo`
  （属于 `TempoHint`，由预设 BPM 与平均密度决定）、`energy`（0..1）、
  `instrumental: true`，以及三种语言的一句描述。
- 只展示，不提交任何请求。按钮链接到 yuha.studio；`/create` 目前不支持通过
  链接预填，第一阶段不改 `apps/web`，预填留到第三阶段。

**iPhone 声音：第一张票，成败点**

- 已证实的事实（见 `apps/web/src/lib/beat.ts`）：iOS 上 Web Audio 走铃声通道，
  **静音键开启时完全无声**，而进度照常前进。正式站的播放器因此在 iOS 上完全
  不用 Web Audio。空气作曲必须实时合成，无法照搬这种回避。
- 候选方案（**均未在真机验证**）：将 `navigator.audioSession.type` 设为
  `'playback'`；在同一次用户手势中启动一个循环播放的静音 `<audio>` 元素，
  使音频会话切到媒体通道。
- AudioContext 必须在第一次 `pointerdown` 的同步处理中创建或恢复。
- 第一张票是一个最小的真机验证（tracer bullet）：iPhone、静音键开启、第一次
  触碰是否发声。如果所有候选都失败，先停下来回到产品层面决策（例如明确
  提示「请关闭静音键」），而不是继续做后面的票。

**语言、无障碍与隐私**

- ja / zh / en，按 `navigator.language` 选择，文案极少。
- 尊重 `prefers-reduced-motion`；画布有可读的说明与开始按钮。
- 不请求任何设备权限，不设 Cookie，不发统计，不写存储。
- 调试开关（链接参数）显示「触碰到发声」的实测延迟，供可用性测试记录。
- 视觉沿用 YUHA 设计系统（`yuha/YUHA_Design_v1` 的设计 token），不使用
  工笔花卉一类与「手势开花」相近的意象。

## Testing Decisions

**什么是好测试**：只通过草图引擎的公开接口测外部行为（帧进、事件出、编码、
描述），不测内部状态、不测私有函数。断言写成音乐上的性质，而不是逐个音符的
快照：快照会把「好听的调整」误报成失败。

**唯一的测试缝：草图引擎**。用 vitest，放在根目录 `tests/`，不需要数据库；
测试直接从应用源码导入，先例是 `tests/ios-audio.test.ts`（从 `apps/web/src`
导入）和 `tests/energy-levels.test.ts`（纯函数、无数据库、对跨边界的取值设
「绊线」）。要验证的性质：

1. **不弹错**：对大量带种子的随机轨迹，每个音符都属于它发生时刻的和弦或
   允许音阶；强拍上只有和弦音。
2. **映射单调**：其他条件相同时，`y` 越高平均音高越高；`speed` 越快音符
   越多；`openness` 越大声场参数越大；`spread` 越大同时发声层数越多。
3. **安静的边界**：没有输入不产生音符；静止输入不产生密集音符；BPM 不随
   `speed` 改变。
4. **确定性与回放一致**：同一草图两次渲染事件完全相同；逐帧实时喂入与整段
   回放产出相同事件；量化后的草图经编码、解码再渲染，与编码前渲染相同。
5. **编解码**：30 秒最坏情况编码不超过 4 KB；任意垃圾输入、截断、未知版本
   均返回「无草图」而不抛错。
6. **参数卡词汇**：`mood` 与 `tempo` 的每个可能取值都属于 `@yuha/contracts`
   的枚举（运行时断言，防止两边词汇漂移）；几条代表性轨迹给出预期的情绪。

**不在自动化测试内、必须在真机上验证的承诺**（按 CLAUDE.md「UI 上的承诺就是
测试」）：

- 「第一次触碰就有声音」：iPhone（静音键开 / 关）、iPad、桌面 Safari、
  Chrome 各测一次，用调试开关记录延迟，留存证据。
- 「回放与刚才一模一样」：现场录屏与回放录屏对比。
- 「不收费」：本页没有任何网络请求（开发者工具网络面板截图）。

**可用性验证（第一阶段的出口）**：5～8 位不懂音乐的参与者，主持人在旁观察，
不提示。记录：第一次触碰到听见声音的秒数、未经提示的探索时长、是否主动点
「让它成为一首歌」。建议的通过线（待产品负责人确认）：

| 验证 | 建议通过线 |
| --- | --- |
| 3 秒内听到令人愉悦的声音 | ≥ 80% 的参与者 |
| 自主探索至少 20 秒 | 探索时长中位数 ≥ 20 秒 |
| 主动希望变成完整歌曲 | ≥ 50% 未经提示点击 |

## Out of Scope

- 摄像头 / MediaPipe 手势模式（第二阶段）。
- 调用正式生成 API、消耗 Credit、`/create` 链接预填（第三阶段）。
- 登录、账号、服务端存储、统计埋点、任何对外可见的计数。
- 放进 YUHA 首页、`apps/web` 或 iOS App。
- 生产域名托管与部署（运营方决定，单列）。
- 导出音频文件、社交平台预览图、公开的作品流。
- 与 Wonderful World 共享代码包、界面或品牌。

## Further Notes

- **与 Wonderful World 的分工**：只共享上文的输入帧约定与隐私原则（摄像头
  默认关闭、仅在用户主动开启后加载、只在本地识别、永不上传）。Wonderful World
  session 负责第二阶段前的摄像头参考说明（MediaPipe 按需加载、权限交互、
  iOS Safari 的坑）。两边都有可用版本后，若输入层确实重复，再考虑抽取共享模块。
- **最大风险**：iPhone 静音键（见上）。其次是「好听」本身无法由自动化测试证明，
  只能由预设设计与可用性测试证明，所以预设需要预留真实的调音时间。
- **建议的票序**（供 `/to-tickets` 细化）：① iPhone 静音键真机验证 →
  ② 引擎骨架：一套预设 + 不弹错 + 单调映射 → ③ 触控输入与声音、光的端到端
  首版 → ④ 演奏流程、回放、重来 → ⑤ 草图编解码与分享链接 → ⑥ 参数卡 →
  ⑦ 其余预设与调音 → ⑧ 多语言、无障碍、调试开关 → ⑨ 可用性测试。
- 本规格按 `to-spec` 流程写成。仓库尚未配置 issue tracker
  （`/setup-matt-pocock-skills` 未运行），因此暂存于 `docs/`，确认后可发布为
  GitHub issue。
