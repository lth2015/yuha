# 等待时先看歌词 — 方案

> 2026-11-24。产品负责人在「下一步做什么」里选了「等待更有感」。

## 核实结果

- **预计时间早就来自真实数据**（2026-10-30，`docs/GENERATION_QUEUE_SPEC.md`，`services/estimate.ts`）：
  最近 7 天同一引擎的实际耗时、前面排几首、已经过去多久都算进去了。这一项不用再做。
- **歌词写好的时间点**：任务从 YUHA 的队列里被放行、送给引擎之前，歌词模型先写歌词（`pipeline.ts` 的意图一步）；
  送给引擎时存进 `generation_jobs.resolved_params`。之后引擎生成要 1–2 分钟，这段时间里歌词已经在服务器上，
  但页面看不到。
- **排队中的任务还没有歌词**：歌词这一步在放行之后才跑。

## 做什么

生成中的页面（首页和创作页的等待页）多一块「歌词写好了」：把这首歌正在录的歌词显示出来。
做好后，歌词在作品页逐行亮起（已有功能），说明里写明这一点。

- `JobView.lyrics`：只在任务交给引擎之后、交付之前（`SUBMITTED` / `PROCESSING` / `UNKNOWN`）有值；
  排队中、已完成（作品上已经有歌词）、纯音乐时为空。列表接口因此不会带上大段文字。
- 取自 `resolved_params.lyrics`，就是送给引擎的那一份：AI 写的歌词已经过内容检查，自己写的就是自己的。
- 只给任务的主人（任务接口本来就只对主人开放）。
- 段落标记（`[verse]` 等）是给音乐模型看的，页面上变成段落之间的空行。

## 不做的事

- 不把歌词这一步挪到排队之前。那样排队时也能看歌词，但取消的任务也要付歌词模型的钱，
  而且要改任务状态机。现在排队通常很短（单人使用时为 0），先不做。
- 不在等待时允许改歌词：引擎已经在录了。

## 验收

- 接口：带人声的任务交给引擎后返回歌词，排队中和交付后不返回；纯音乐不返回；别人看不到任务（404）。
- 页面：360 px 宽、三种语言都不溢出；段落标记不显示。
