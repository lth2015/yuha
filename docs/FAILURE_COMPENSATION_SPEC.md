# 失败补偿记录 — 规格

> 2026-10-30。顺序里的第三项：私密问题反馈 → 任务找回 → **失败补偿记录**。
> 「失败后的积分处理要能从账本核对。」这一项让用户和团队都能核对同一本账。

## 现在缺什么

- **系统一直在补偿，但只记在账本里，谁都看不到。**
  - 生成失败时额度退回原批次（`release`）。
  - 原批次在生成过程中过期时，补发一个新批次（`compensate`）。
  - 用户只能看到一张「批次」表，看不出哪一首失败退回了、哪一首补发了。
- **歌生成了但有问题（漏唱、歌词错位、杂音），没有办法补偿。**
  - 这种情况额度已经按「已使用」结算。
  - 后台有一个 `POST /v1/admin/users/:id/compensate` 接口，但没有任何界面，问题报告也不能顺手补偿。
  - 用户在报告里只能看到一句处理说明，看不到额度有没有回来。
- **客服核对不了额度。** 后台的客户页列出最近的任务，只有状态和错误码，看不到这个任务的额度最后怎样了。

## 要做到什么

### 用户：「额度记录」

`/settings/billing` 的额度区下面增加「额度记录」，数据来自 `GET /v1/credits/history`。
范围是本人最近 180 天，最多 100 条，按时间倒序。

| 种类 | 显示 | 变化 |
| --- | --- | --- |
| 一次生成 | 歌名（或描述），结果来自账本：已使用 / 已退回 / 原额度过期已补发 / 结算中 | −1 或 0 |
| 获得额度 | 购买、订阅、试用、重置、赠送、调整 | +n |
| 客服补偿 | 「客服补偿」，有关联的歌时显示歌名和报告编号 | +n |
| 退款收回 | 订单退款时收回未用的额度 | −n |

- **一次生成只占一行。** 暂扣、使用、退回是同一件事的几个步骤，拆成几行反而看不懂。
- **过期补发合并在那一次生成的行里。** 不另列一行「+1」，否则同一首歌看起来像补了两次。
- **客服填写的内部原因不给用户看。** 用户看到的是问题报告里的处理说明。
- 每行都能点进去：
  - 有作品的打开歌曲页；
  - 没有作品的打开任务页，也就是「任务找回」的失败页。

### 团队：处理问题报告时补偿

后台「审核」页处理问题报告时，可以勾选「补偿 1 首额度」：

- 补偿记在这首歌的生成任务上（`compensate` 记录带 `job_id`）。账本对同一个任务只允许一次补偿，所以同一首歌不会被补偿两次。
  - 这首歌已经补偿过时，接口返回 409，什么都不改。员工可以不勾补偿，直接处理完成。
- 和后台已有的补偿一样受每日上限（`ADMIN_COMPENSATION_MAX_UNITS_PER_DAY`）约束，写审计日志。
- 处理完成和补偿在**同一个事务**里：要么都成功，要么都不发生。
- 报告上记下补发的批次。用户在歌曲页的报告历史里看到「已补偿 1 首额度」，额度记录里也多一行「客服补偿」。

### 团队：客户页核对额度

后台客户页的「最近的生成」表增加两列：

- **额度**：来自账本的结果，和用户看到的完全一致。
- **任务编号**：用户报给客服的编号，在这里能对上。

每一行有「补偿 1 首」按钮，用的是已有的补偿接口，带上任务 ID，需要填写原因。

## 不做的事

- 不做自动补偿规则（例如「漏唱自动退款」）。有没有问题由人听过之后判断。
- 不把员工填写的补偿原因展示给用户。
- 不改账本结构。只给问题报告加一列，记下补发的批次。

## 验收

- 失败退回、过期补发、成功使用、客服补偿、退款收回，在「额度记录」里各显示一次，数字和账本一致。
- 处理问题报告时补偿：额度加 1，报告显示已补偿，审计日志有记录；对同一首歌再补偿一次返回 409，额度不变。
- 补偿遇到每日上限时，报告也不会变成「已处理」。
- 别人看不到你的额度记录。
- 三种语言，360 / 393 / 768 / 1280 宽度（`pnpm check:ui`）。
