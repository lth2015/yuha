# 额度重置（Credit reset）

2026-10-27，产品负责人提出，按其确认的四条规则实现。

## 规则

| | |
|---|---|
| 什么时候重置 | **运营者手动**，在后台「运营」页点「重置」，没有自动定时。 |
| 补足 | 每个正常账号（`status = active`、未删除）**按总余额**补到 `CREDIT_RESET_FLOOR`（默认 5）：自己买的、订阅的、赠送的都算。已经有 5 个或以上的不补。 |
| 付费多送 | **上次重置以来**付过费的账号（买了充值包，或订阅续费成功，且没有被全额退款）再多送 `CREDIT_RESET_PAID_BONUS`（默认 5）。第一次重置往前看 30 天。先补足、再多送：一个余额为 0 的付费用户拿到 10 个。「全额退款」按钱判断：充值包订单状态为 `refunded`，或这期订阅已记录的退款达到这期的价格。部分退款仍算付过费（2026-10-29 起；之前按额度是否被全部撤销判断，买了用掉一次再全额退款的人仍会被多送）。 |
| 过期 | 重置发的两部分都**在下一次重置时作废**；不累积。用户自己买的、订阅的额度不受影响。 |
| 先用哪个 | 重置发的额度**最先被用掉**，然后才按到期先后用其他额度。否则用户会先花掉自己买的，免费的那部分反而在下次重置时被清掉。账单页的表格和说明按同一顺序显示。 |

## 怎么用

后台 →「运营」→「额度重置」卡片（只有 admin 看得到）：

1. 卡片上先显示「现在重置会怎样」：多少账号、补多少个、多少付费账号多送多少个、付费从哪天算起。这些都是实时算出来的。
2. 填原因（写进审计日志），点「重置」，确认框会再说一遍总共发多少个。
3. 重置在服务器后台逐个账号执行，卡片显示进度；结束后在下面的表里留一行记录。
4. 如果中途服务重启，卡片会显示「上次重置没有跑完」和「继续」，点继续会从停下的那个账号接着做，不会重复发。

同一时间只能有一个重置在跑；没跑完的必须先「继续」做完，才能开始新的。

## 实现

- `POST /v1/admin/credit-resets`（admin）开始一次重置，或用同一个 `idempotencyKey` 继续它，立刻返回 202，后台执行。`GET /v1/admin/credit-resets` 返回预览和最近 10 次，`GET /v1/admin/credit-resets/:id` 返回一次重置的进度。
- 账本来源是新的 `credit_reset`（迁移 0023），和 `operator_gift`、`compensation` 分开，「重置一共送了多少」是一条查询。每个账号一笔 `…:floor`、一笔 `…:bonus`，靠 (user, source, source_ref) 唯一键保证不会发两次。
- 每个账号一个事务：锁住账号 → 把以前重置的额度的到期时间设为现在（和其它额度一样按日期失效，账本对账不受影响）→ 按余额补足 → 判断是否付费、多送 → 推进重置的游标。中断后从游标继续。
- `reserveUnit` 和 `listBatches` 都把 `credit_reset` 排在最前面。
- 开始和结束各写一条审计日志（`credit_reset.started` / `credit_reset.finished`，附数量）。
- 测试：`tests/credit-reset.test.ts`（补足、多送、作废、优先使用、幂等、中断续跑、预览与实际一致、权限与审计、账本对账）。

## 成本

每个 credit 是一次真实的生成。一次重置最多发出「账号数 × 5 + 付费账号数 × 5」个，卡片在点之前就给出准确数字。这部分额度用掉才产生成本，没用掉的下次重置时作废。

## 两个进程同时跑（2026-10-29）

每处理一个账号，都先在同一事务里锁住这次重置的行并确认它还在 `running`。之前防止重复运行的只是
单个进程内的集合：两个 API pod 时，一个进程还在处理 A 的账号，A 已被另一个进程跑完、管理员又开始了 B，
慢的那个处理下一个账号时会把 B 刚发的额度一起过期，而 A 的补足已经发过，账号就变成 0。现在 A 结束后
它什么都不做；而且过期只针对创建时间更早的重置。
