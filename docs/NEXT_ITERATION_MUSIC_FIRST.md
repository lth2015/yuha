# YUHA 下一迭代执行计划：自动歌词同步优先

2026-11-26 · 负责人共识与 Codex 执行拆分 · 核对远端主干 `37bd969`。

**这一迭代的首要交付是有人声歌曲的自动歌词同步。** 用户生成歌曲后直接播放，YUHA 在后台校准并应用时间轴。波形和游标服务于听歌和音轨编辑，打开编辑器、逐行拖动、确认和保存都不是交付步骤。照片与封面 MV 继续服务歌曲分享。Veo 实现可以保留在可复用的稳定提交，新增页面、投入和公开推广排在这轮歌词交付之后。

本文件是当前排期与线上交接入口。产品取舍、实验设计和独立评审见 [方向复盘](MUSIC_FIRST_DIRECTION_REVIEW.md) 与 [Claude #147](https://github.com/lth2015/yuha/pull/147)。

## 这轮用什么判断完成

- **用户动作。** 新歌自动开始和应用，刷新后还在。旧歌遇到缺失或估算时可自动补齐。用户直接播放即可，整首重试是异常时的选项。
- **实际歌声。** 用同一批中日英测试音频对照歌词起点、重复副歌、间奏、漏唱和改词。对齐中和失败状态保持诚实。未确认行仅降级显示，整首未达标计入失败。挂了 `aligned` 标签不能替代试听。
- **同一交付。** 页面高亮、拖动后位置和导出字幕使用同一交付音频与有效版本。遇到暂未确认的同步可直接导出无字幕版本。
- **决策数据。** 按语言报告整首零操作可用率、首播时同步就绪率、音频就绪到同步可用的耗时，以及超时、误高亮和实际成本。先测当前基线，由 Claude 和 Codex 用盲听证据约定小范围发布前的绝对目标。临时降级和小样本均单列。

## 给 Claude 的线上同步要求

**每批通过 CI 和交叉验收的可发布更新，按仓库现有节奏及时推进到线上。** 提交、CI、合并、生产生效是分别可核实的状态。小批次能单独发布就先发布，特别是版本写入保护。需要先开小范围或观察后再扩大的改动，明确当前覆盖人群和下一次观测。

1. **发布前**在 PR 留实现 SHA、测试结论、兼容性、回退方式以及是否依赖 DGX。当前仓库的 `Deploy QA` 对应生产 `yuha.studio`，主干进入发布流程。跨版本字段先保持兼容。
2. **发布后**跟进部署工作流到结束，核对生产实际版本、服务就绪和本批用户路径。网页、API、worker 或 DGX 哪部分变了就验证哪部分。若更改 DGX 对齐器，单独跟进对齐服务的部署版本和一次实际对齐请求。生产网页更新不能据此证明 DGX 已更新。
3. **同一协作入口回报** PR 链接、部署运行链接、生产 build SHA、确认时间（JST）、开关或实际覆盖范围、真实验收结果、剩余阻塞。部署失败或线上版本未变要当天同步阻塞、负责人与下一步；依当前回退流程处理，恢复后再更新回执。待验收时准确标为「已部署，待在线验证」。报告只放脱敏证据。

公开扩大覆盖依自动同步实测表现推进。已有 Veo 分支和草稿 PR 的技术状态可以按原协作方式更新，当前发布计划的优先队列以歌词为准。发布与取证沿用 [现有部署流程](../.github/workflows/deploy.yml) 及 [歌词对齐运行说明](LYRIC_ALIGNMENT.md)。

本次为文档与执行交接。应用实现、生产发布、上线验收和实际付费测试由后续对应批次完成。
