## Problem Statement

用户在空气作曲里玩出了一段让自己满意的情绪，点「让它成为一首歌」，看到参数卡，再点
「去 YUHA」，结果落在 yuha.studio 的首页：一个空白的输入框。刚才的感觉要用户自己重新
说一遍，而说不出感觉正是空气作曲想替他们解决的问题。第一阶段在这里断了线。

## Solution

1. 参数卡上的按钮打开 `yuha.studio/create`，地址里带上这次草图的参数。
2. 没登录的人先登录（或注册），登录后回到同一个地址。这条路现在就是通的。
3. `/create` 读取参数，把表单填好：
   - **描述**：用用户的界面语言写出这段草图的感觉，例如「一段明亮、开阔、中速流动的
     纯音乐，情绪自信」；
   - **纯音乐**：打开；
   - **能量**：选中对应的那一档（舒缓 / 适中 / 强烈）；
   - 其他（时长、风格标签、可见性）保持默认，由用户自己决定。
4. 页面上方有一行说明：「这是你在空气作曲里的草图，确认或修改后点生成」。
5. **用户自己按「生成」才会生成**，按下之前不发任何请求，不扣任何 Credit。
6. 如果用户在 `/create` 里已经有没写完的草稿，**不丢失它**：表单按草图填好，旧草稿先收起来，
   提示条上可以一键「恢复之前的草稿」。（2026-10-27 改：原来是先问二选一，表单停在旧草稿上，
   产品负责人试用时选了纯音乐、跳过去却还是人声。按「去 YUHA」本身就是在选这份草图。）

## User Stories

1. 作为刚玩完空气作曲的人，我希望点「去 YUHA」后看到已经填好的表单，以便不用重新描述刚才的感觉。
2. 作为不懂音乐的人，我希望表单里的描述是我看得懂的话，而不是参数，以便知道它理解了我。
3. 作为用户，我希望预填的描述用我自己的语言（中 / 日 / 英），以便读得懂。
4. 作为用户，我希望能修改预填的描述、能量和时长，以便把草图调成我想要的歌。
5. 作为用户，我希望在按下「生成」之前不会发生任何生成或扣费，以便放心查看。
6. 作为没登录的人，我希望登录或注册后直接回到填好的表单，以便不用回去重新点一遍。
7. 作为在 `/create` 里写了一半草稿的人，我希望空气作曲的链接不会让我丢掉自己的草稿，以便需要时能拿回来。
8. 作为用户，我希望刷新页面后，我对预填内容的修改不会被链接里的参数重新覆盖，以便修改不白做。
9. 作为用户，我希望知道这张表单是从空气作曲来的，以便明白为什么它已经填好了。
10. 作为 Credit 不足的用户，我希望照样看到填好的表单，并看到和平时一样的「余额不足」提示，以便决定是否购买。
11. 作为收到一个被人篡改过的链接的用户，我希望页面只接受合法的参数，以便不会被填入奇怪的内容。
12. 作为 YUHA 的维护者，我希望这个入口不改变生成请求的格式和扣费逻辑，以便不影响现有用户和账本。
13. 作为 iOS App 用户，我希望这个改动不影响 App 的行为，以便 App 的发布节奏不受打扰。
14. 作为运营方，我希望能知道有多少生成来自空气作曲（只在服务端，不对外展示），以便评估这个入口。（见「待决定」）

## Implementation Decisions

**链接只带枚举值，不带任何自由文本**
- 空气作曲生成的链接只包含这几个值：版本、情绪（`Mood` 的 8 个值之一）、速度
  （`TempoHint`）、能量档位（`ENERGY_LEVELS` 的 id）、明暗（bright / soft / deep）、
  空间（wide / close）、纯音乐标记。
- **描述文字由 `/create` 用自己的多语言词典生成**，不从链接里读。这样：
  - 被篡改的链接最多只能换成另一组合法的枚举，填不进任意文字；
  - 描述永远是用户界面的语言，不受分享者语言影响；
  - 链接很短。
- 链接的格式由 `@yuha/contracts` 里的一个 zod schema 定义（例如 `airPrefill`），
  `/create` 用它校验。任何一项不合法，整个预填作废，按普通 `/create` 打开，并给一行提示。
  不做「部分接受」。

**空气作曲这一端**
- 用 `new URL('/create', 'https://yuha.studio')` 构建链接并设置查询参数，**断言 origin 没变**
  （CLAUDE.md：拼接路径不等于构建 URL）。
- 仍然只引用 contracts 的类型，不把 zod 打进空气作曲的页面。用跨边界测试保证空气作曲
  生成的链接能通过 contracts 的 schema（与第一阶段参数卡的做法相同）。

**`/create` 这一端**
- 只新增一个查询参数（例如 `air`），与现有的 `edit`、`job` 并列；三者同时出现时
  `edit` 和 `job` 优先，`air` 被忽略。
- 预填在 **draft 的惰性初始化里完成，不放在 effect 里**。CLAUDE.md 记录过 load 与 save 两个 effect
  竞争、每次加载都把草稿清空的事故。
- 有没写完的草稿（描述或歌词非空）时，表单照样按草图填好，旧草稿留在页面内存里，
  提示条给出「恢复之前的草稿」。提示条还按人声 / 纯音乐各说一句这个选择意味着什么。
- 预填应用之后，用 `history.replaceState` 去掉地址里的 `air` 参数，刷新不会再次覆盖用户的修改。
- 能量直接设为档位对应的值（0.2 / 0.5 / 0.85），表单上对应的选项会显示为选中。
- 不新增生成请求的字段，不改 `/v1/generations`，不改扣费与账本逻辑。
  情绪和速度只体现在描述文字里，这正是现有生成链路读取它们的方式（由意图解析从描述里得出）。

**登录**
- 不需要改。`RequireAuth` 已经把完整路径和查询参数带过登录（邮箱、Google、MFA 都覆盖），
  `safeInternalPath` 已经拦住站外跳转。

**iOS**
- 不在范围内。iOS 外壳没有 `/create`，也不处理外部链接；`applinks:yuha.studio` 已声明，
  但仓库里没有 `apple-app-site-association` 文件，所以这个链接在 iPhone 上会用浏览器打开。
  **风险**：如果以后为 iOS 加上 Universal Links，`/create?air=…` 会落到 iOS 的占位页。
  届时要么排除这个路径，要么让 iOS 支持它。

**与上线 yuha.studio 的关系**
- 本阶段不依赖空气作曲本身托管在哪里。无论它在 claude.ai 托管页还是 `yuha.studio/air`，
  链接都指向 `yuha.studio/create`。

## Testing Decisions

**好测试的标准**：只测外部行为。链接进 → 表单状态出；不测组件内部状态。

**唯一的测试缝：一个纯函数**，例如 `draftFromAirPrefill(param, lang, storedDraft)`，
返回「要填的草稿（以及有没有旧草稿被收起）」或「不合法，忽略」。测试覆盖：

1. 合法参数 → 纯音乐打开、能量是三档之一的精确值、描述是该语言的文字且不超过
   `PROMPT_MAX_CODEPOINTS`、其他字段保持默认。
2. 三种语言下描述都非空；8 种情绪、3 种速度的每个组合都有文字（不出现漏掉的键）。
3. 已有非空草稿 → 返回「冲突」，绝不直接覆盖。
4. 不合法参数（未知情绪、能量不是三档之一、缺项、多余项、超长、未知版本）→ 整体忽略，不抛错。
5. **跨边界绊线**：空气作曲生成的每一种链接都能通过 contracts 的 schema；schema 的取值与
   `Mood`、`TempoHint`、`ENERGY_LEVELS` 一致。
6. 空气作曲端的链接构建：origin 不变、只含允许的参数。

**界面实测**：`scripts/check-ui.mjs` 的 PAGES 增加一项预填状态的 `/create`（三种语言 × 四种宽度），
包括冲突提示的状态。现有的 `routesCovered()` 会去掉查询参数，不会强制要求这一项，所以要手动加。

**承诺即测试**（CLAUDE.md）：
- 「按下生成前不扣费」：用测试账号打开预填页面、不按生成，读账本确认余额没有变化。
- 「不覆盖草稿」：先在 `/create` 写一段描述，再打开空气作曲链接，确认原文还在。
- 「登录后回到表单」：未登录打开链接，走一遍邮箱登录和 Google 登录，确认落在填好的表单上。

## Out of Scope

- 自动生成（不经用户按下「生成」）。
- 在生成请求里新增情绪 / 速度字段，或修改音乐服务。
- iOS App 内的空气作曲入口与 Universal Links。
- 把空气作曲并入 `apps/web`。
- 摄像头输入（第二阶段）。
- 把演奏本身（草图）存到用户账号里或附在生成的歌上。

## Further Notes / 待决定

1. **来源统计**：要不要在生成请求里记录「来自空气作曲」，供运营方在服务端统计？这会给
   请求加一个字段，触及 contracts 和 API。只在服务端记录、绝不对外展示（符合「不显示计数」
   的原则）。由产品负责人决定；默认不做。
2. **描述文字的写法**：例如中文「一段{明暗}、{空间}、{速度}的纯音乐，情绪{情绪}」。
   具体措辞在实施时用几组组合交给产品负责人确认，因为它直接决定生成出来的歌。
3. **时长**：默认保持 2:00，还是根据草图长度或能量推荐？建议保持默认，交给用户。
4. 预计切分（实施时用 `/to-tickets` 细化）：
   ① contracts 的 schema 与跨边界测试 → ② `/create` 读取与冲突处理 →
   ③ 空气作曲端改链接 → ④ check:ui 与承诺实测 → ⑤ 产品负责人确认描述文字。

## 实施记录（2026-10-26）

**待决定的三项**：来源统计不做；描述文字已给产品负责人看过，可再调（全在 `apps/web/src/lib/i18n.tsx` 的
`create.air.*`）；时长保持默认 2:00。

**链接第 2 版：从演奏到一首有词的歌**。产品负责人要求「通过点击的记录去生成歌曲，让 AI 写素材或歌词」，
在不新增服务端 AI 调用、不改生成接口的前提下这样实现：

- 参数卡上新增一个选择：「有人声」（默认）/「纯音乐」。选「有人声」时，`/create` 填成有人声、AI 写词。
  AI 写词正是生成链路对任何有人声请求本来就做的事。
- 演奏的走向成为素材：手的高度在开头、中段、结尾的变化，归为「从低处慢慢扬起 / 从高处缓缓落下 /
  起伏回旋 / 始终平稳」四种之一（`describe.ts` 的 `arcOf`），写进描述里。音乐和 AI 写的歌词都从这段描述出发。
- 链接格式：`2-<mood>-<tempo>-<energy>-<tone>-<space>-<arc>-<voice>`。第 1 版链接仍然可以打开，
  按纯音乐、不含走向处理，与当时的含义一致。
- 实测：在演示环境里用「有人声」的链接填好表单，按「生成歌曲」后生成了含人声的歌，额度正好扣 1 次。

更进一步的做法（由服务端 AI 先根据整段演奏写一段故事性的素材，再写词）需要新增 AI 调用和成本，
没有做，需要时另写规格。
