# 照片 MV — 方案（第一期）

> 2026-11-23。产品负责人转述朋友的建议：「聚会、旅游、婴儿照、结婚照……照片很分散，时间长了就不看了。
> 有这个音乐 + 照片的模式，很容易让人生成内容发一发。」产品负责人：「去做吧。」
> 分三期（照片 MV → 看图写歌 → 照片场景页），这里是第一期。

## 一句话

歌做好后，在歌曲页选 3–10 张照片，YUHA 把它们配上这首歌，做成一段 30 秒的竖版视频：照片随时间换页，
歌词逐句出现在下方，可以直接下载或发到 TikTok、Instagram、X、LINE。

## 现有的底子

分享视频（`GIFT_AND_SHARE_SPEC.md` 第三部分）已经是这个流程：

1. 浏览器画每一帧（720×1280 JPEG）：封面、歌名、正在唱的那句歌词；
2. 发给 API 的 `POST /v1/tracks/:id/share-video`；
3. API 用 ffmpeg 把这些帧接起来，配上这首歌的音频和一条随音乐动的波形，返回 MP4；**不保存任何东西**（临时目录在 `finally` 里删除）。

照片 MV 只把第 1 步的画面从「封面」换成「照片」，第 2、3 步复用。

## 怎么做

| 项 | 规则 |
| --- | --- |
| 谁能用 | 歌的主人，歌已经可以播放（`deliverable`）。公开、私密都可以（视频是文件，不是链接） |
| 照片数 | 3–10 张，按选择的顺序播放 |
| 长度 | 30 秒；有标注副歌就从副歌前开始，和分享视频的选段规则相同（`planShareClip`） |
| 换页 | 照片平均分配这 30 秒；歌词换句时也换一帧，照片不变 |
| 画面 | 照片铺满画面（居中裁切），上方 YUHA 标志，下方渐暗，歌名和正在唱的歌词用白字；底部波形和网址 |
| 照片处理 | 在浏览器里解码、按拍摄方向转正、缩到 1440 px 以内；只有画好的整帧 JPEG 发给服务器 |
| 不保存 | 服务器只在合成的几十秒里在临时目录里有这些帧，合成完即删；不写数据库、不写对象存储、不进日志、不交给任何 AI 模型 |
| 提示 | 选照片的地方写明：「请只用你有权使用的照片。照片只用来合成这段视频，不会被保存。」 |
| 开关 | `FEATURE_PHOTO_VIDEO_ENABLED`，默认关闭。隐私政策修改稿（`docs/legal/PRIVACY_CHANGES_2026-11.md`）审定之前不打开 |

服务器端：新接口 `POST /v1/tracks/:id/photo-video`，和分享视频同一个合成函数，限制不同：

- 开关关闭时返回 `SERVICE_DISABLED`；
- 只有主人；
- 时长 10–30 秒，帧数最多 40，请求体最多 16 MB（40 帧照片 JPEG 的上限）；
- 每个 API 进程同时只合成一个（和分享视频共用同一把锁），第二个请求得到 429。

## 不做的事（这一期）

- 不让 AI 看照片（第二期「看图写歌」单独征求同意）。
- 不保存照片、不保存视频、不做「我的视频」列表。
- 不做转场特效和缓慢推近：一期先把换页和歌词同步做对；推近需要每秒多帧，上传量会翻几倍。
- 访客（非主人）不能做。

## 验收

- 测试：选段和换页的计划（照片数、歌词换句、时长）是纯函数，单独测；接口：开关关闭被拒、非主人被拒、
  超限被拒、合成后临时目录为空。
- 手机上：选 5 张照片 → 30 秒内拿到 MP4 → 系统分享面板能发出去；横拍、竖拍、带方向信息的照片都转正。
- `pnpm check:ui`：歌曲页在开关打开时（预览）多出的「照片 MV」入口不溢出。
