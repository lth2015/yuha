# BGM 人工评审（30 条）

[BGM_STUDIO_PLAN.md](../BGM_STUDIO_PLAN.md) 验收用的人工评审，回答三个问题：

1. 生成的 BGM 有多少能直接拿来用；
2. 哪些选项组合效果差；
3. B2 的"可能含人声"提示，阈值 `BGM_VOICE_SECONDS_MAX` 定在多少，提示才很少出错。

## 样本

[`bgm-review-set.json`](bgm-review-set.json) 是固定的 30 组选项：
- 7 种场景、7 种风格、6 种情绪、3 种时长、3 种节奏，每一项都出现 4 次以上；
- 第 1 组是页面的默认值（Vlog / 日系治愈 / 温暖 / 30 秒）。

每一组都用**员工账号**在 `/bgm` 生成一首，补充描述留空。样本固定下来，下一次评审（换模型、改提示词模板之后）才能和这一次直接比较。

生成后，把每首 BGM 设为「凭链接可打开」。别的评审人才能用表格里的链接打开它。这些是员工做的测试曲目，没有公开列表，拿到链接才能听。

## 流程

1. **导出评审表**（在产品负责人的电脑上，和 `pnpm check:invariants` 一样用生产库的只读连接）：

   ```bash
   pnpm bench:bgm-sheet quality-probes/bgm-review
   ```

   - 只导出员工做的 BGM，用户的 BGM 不会出现。
   - 一首都没有时直接报错，不会生成空表格。
   - 写出三个文件：
     - `sheet.csv`：评审人要填的表，只有选项和链接；
     - `meta.json`：每首的选项，用于分组统计；
     - `quality.json`：DGX 测出的数据。单独存放，评审时不要看，以免先入为主。
2. **评审**：每人复制一份 `sheet.csv` 到 `reviews/<名字>.csv`，填 `reviewer` 列和各项评分。
   - 戴耳机，每首至少完整听一遍。
   - 至少两个人听同一批，才能算出两人的一致率；一致率太低，说明标准没有讲清楚。
   - 只听了一部分也可以，没填的行会被跳过。
3. **出报告**：

   ```bash
   node scripts/bgm-review.mjs quality-probes/bgm-review
   ```

## 评分项

1–5 分：1 = 完全不符合，3 = 勉强可以，5 = 完全符合。

| 列 | 问的是 |
| --- | --- |
| `fitsBackground` | 能不能垫在旁白或对话下面，不抢戏：没有突出的主旋律，音量没有忽大忽小 |
| `fitsScenario` | 适不适合所选的场景（旅行、美食……） |
| `fitsGenre` | 听起来是不是所选的风格 |
| `fitsMood` | 是不是所选的情绪 |
| `soundQuality` | 音质：有没有爆音、失真、明显的电子瑕疵 |
| `cleanEdges` | 开头和结尾干不干净：有没有突然开始、突然断掉 |
| `voiceHeard` | yes / no：有没有听到人声，包括哼唱、念白、像人声的音色 |
| `usable` | yes / no：如果你在剪视频，会不会**直接**用它 |
| `note` | 可选，写听到了什么问题。含逗号时整格用英文双引号括起来 |

**判定规则**：每首按评审人的多数意见判定；如果两人意见相反（平票），按"否"算。"可以直接用"和"没有人声"都是我们要对外承诺的，平票撑不起这个承诺。

## 报告给出什么

- **直接可用的比例**，以及**听到人声的比例**。
- **各评分项的平均分**。
- **按场景、风格、情绪、时长、节奏分组的可用比例**：看哪个选项拖了后腿。
- **两人一致率**：只算被两个人以上听过的那些首。
- **人声阈值校准**：每个候选阈值下，DGX 的判断和评审人的多数意见对得上多少。
  - "精确率"：提示"可能有人声"的那些首里，真有人声的占多少；
  - "召回率"：真有人声的那些首里，被提示出来的占多少。
  - 建议取精确率够高的最小阈值，再把没提示出来的那几首逐一听一遍。
  - 这一项需要 B2（#163）上线、而且 DGX 已经更新；在那之前，报告里会写明"没有测量数据"。

## 局限

- 30 首能看出明显问题，但比例的误差还很大：30 首里 20 首可用，真实的可用比例可能在 50% 到 80% 之间。拿报告做决定时要考虑这一点。
- 评审人都是自己人，听惯了 YUHA 的风格，评价可能偏宽。
