# 固定测试歌曲 — 执行单

> 路线图第三项的后半：「建立一组固定的中日英测试歌词，定期检查漏字、人声、杂音和结尾截断。」
> 执行人：Codex（生成和自动检查），产品负责人或 Codex（试听）。分工见
> [docs/agents/CODEX_COLLABORATION.md](../agents/CODEX_COLLABORATION.md)。

## 测试集

[`probe-set.json`](probe-set.json)：中、日、英各两首，每首 60 秒、有人声，歌词都是为测试原创的。

| ID | 测什么 |
| --- | --- |
| `zh-numbers` / `ja-numbers` / `en-numbers` | 数字、英文缩写、片假名、缩约形混在歌词里：强制对齐最难的部分 |
| `zh-ballad` / `ja-ballad` / `en-ballad` | 普通抒情，作为对照 |

**歌曲不改，只加。** 结果按 ID 跨时间比较。要换一首就用新 ID，旧 ID 留着，这样历史结果仍然能对上。
测试集本身有测试（`tests/quality-probe.test.ts`）：三种语言各两首、API 接受这些请求。

## 什么时候跑

- 每周一次；
- DGX 上的模型或对齐服务更新之后（例如跑过 `./update.sh`）；
- 和生成相关的 PR 上线之后。

一次 6 首，花 6 首额度。用运营方自己的测试账号，不用真实用户的账号。

## 怎么跑

1. 在 yuha.studio 用测试账号登录，从浏览器开发者工具的 `localStorage['loopscene.token']` 复制会话令牌。
   令牌只放在环境变量里，不要写进任何文件。
2. 先试运行，不花额度，确认账号、额度和要生成的歌：

   ```bash
   YUHA_TOKEN=… pnpm probe:quality
   ```

3. 生成并自动检查（一首一首来，每首等到完成，总共大约 10–30 分钟）：

   ```bash
   YUHA_TOKEN=… pnpm probe:quality --spend
   ```

   同一天再跑一次，拿回的是同一批歌，不会重复扣额度。某首失败要重试，就加 `--attempt 2`（会生成新歌，花新额度）。
4. 报告写在 `quality-probes/<日期>.md`（不进 git）。里面有：
   - **自动检查**：时长达标、时间轴是「对齐」而不是「估算」、每一行都有时间、时间轴在歌曲范围内、顺序正确；
   - **试听清单**：每首一节，附歌曲链接。

## 试听

每首歌打开、显示歌词、从头听到尾一遍，勾选：

- [ ] 每一行都唱了（没有漏字、没有换词）
- [ ] 有人声，而且是要求的那种（男声 / 女声）
- [ ] 没有杂音、爆音或断音
- [ ] 结尾没有被截断
- [ ] 高亮的那一行跟得上演唱（跟不上的话记下时间 mm:ss）

## 结果放在哪里

- 把报告整份贴进一个 GitHub issue，标题为「quality probe <日期>」，附后台显示的 build SHA。报告里只有任务和歌曲 ID，可以公开。
- 试听发现的问题按协作说明里的报告格式写。能写成规则的（例如「交付的人声歌时长 ≥ 要求的 90%」），按「新规则从哪里来」那一节交给 Claude。
- 同一首歌连续两次出同样的问题，就不是偶然，应当作缺陷处理。
