# Claude 和 Codex 的协作说明

> 2026-10-30。YUHA 由两个 AI 代理一起开发：Claude（Claude Code，在云端容器里）和
> Codex（在产品负责人的电脑上）。两边互相看不到对方，只能通过仓库、PR 和产品负责人传话。
> 这份说明规定：谁做什么、结果放在哪里、用什么格式，好让一方的发现另一方马上就能处理。

## 分工

| | Claude | Codex |
| --- | --- | --- |
| 主要做 | 写规格、实现、测试，开 PR，合并后跟进部署 | 评审 PR，在线上做验收和安全测试 |
| 能接触到 | 仓库、CI、本地测试库、线上的公开页面和接口 | 产品负责人的浏览器和登录状态、线上后台、DGX |
| 碰不到 | 登录后的线上状态、真实支付、钱包、DGX | 这个云端会话 |

**两边都做逻辑检查。** 判断代码是否符合逻辑，不靠「看起来对」，而靠下面的「逻辑规则」。

## 逻辑规则：不能同时出现两个太阳

产品里有一些事情在任何时候都不能同时成立，就像白天不能有两个太阳、白天看不见星星。
这类规则要**写进代码**，由机器检查，不靠人记。

### 规则怎么写

- **每条规则是一个 SQL 查询，返回所有违反它的数据。** 查到 0 行才算通过。
- **每条规则都要有一个「反例测试」**：故意写进一行违反它的数据，确认检查真的能抓到。只有「通过」、没有「抓到过」的检查，可能根本什么都没在查。CLAUDE.md 里记过两次这种教训。
- 规则用一句中文说清楚，再写一句为什么。
- 检查命令是 `pnpm check:invariants`，可以对任何数据库运行：本地、测试库，或生产库的只读连接。后台「运营指标」也会显示每条规则当前的违反数。

> **状态（2026-10-30）**：规则清单已定，命令和后台显示是下一步要实现的。在那之前，下表是两边
> 评审和验收时人工核对的清单。

### 第一批规则

| 规则 | 为什么 |
| --- | --- |
| 交付了的任务一定有作品 | 用户看到「完成」却找不到歌 |
| 交付了的任务一定已结算额度（`consume`） | 否则额度一直被暂扣 |
| 失败、被拒、取消的任务从不扣额度 | 失败不收费（§6.1） |
| 结束了的任务不再暂扣额度：有暂扣，就有退回或使用 | 额度不能悬在半空 |
| 一个任务不能既「已使用」又「已退回」 | 同一份额度不能花两次 |
| 进行中的任务还没有结算 | 结果没出来就不能下结论 |
| 有结束时间，当且仅当任务已经结束 | 状态和时间要说同一件事 |
| 批次的暂扣加已用不超过发放数 | 不能透支 |
| 批次的计数和账本一致 | 账本是唯一真相（已有每日对账） |
| 付了钱的订单发放过一次额度；没付钱的订单什么都没发 | 付钱才发货，只发一次 |
| 全额退款的订单没有留下还能用的额度 | 退了钱就收回没用的部分 |
| 歌的主人就是生成它的人 | 不会把别人的歌算到你名下 |
| 已处理的报告有处理时间和说明；未处理的报告没有补偿 | 状态和内容一致 |
| 报告上的补偿批次属于报告的主人，来源是「补偿」 | 补偿不会发错人 |
| 绑在任务上的补偿，批次也指向同一个任务 | 每首歌最多补偿一次（`job:<id>`） |

### 新规则从哪里来

**发现一个逻辑缺陷，先把它写成一条规则（或一个测试），再修。** 这样它以后再出现，检查会先发现。

- Codex 在验收中发现「这两件事不该同时成立」，在报告里用下面的格式写出规则。
- Claude 把规则写进代码，加上反例测试，再修缺陷。

## 结果放在哪里

| 内容 | 放在 | 原因 |
| --- | --- | --- |
| 代码缺陷、逻辑问题、建议（不含真实用户信息） | PR 评论，或 GitHub issue | Claude 订阅了自己开的 PR，评论一到就处理 |
| 含真实用户、订单、钱包、后台截图的内容 | 只留在本机，由产品负责人贴给 Claude | **仓库是公开的** |
| 安全漏洞的细节和复现 | 只留在本机，由产品负责人贴给 Claude | 修好之前不公开 |

运营者（yuha.studio 的经营者）本人的姓名、地址、电话和邮箱，不写进任何文件，包括 PR 评论
（见 CLAUDE.md 和 `pnpm check:stewardship`）。

## 报告格式

每条发现单独写，按严重度从高到低排：

```
[高 / 中 / 低] 一句话说明问题
- 现象：看到了什么（不含真实身份的复现步骤）
- 应该：本来应该怎样
- 违反的规则：（新规则就写一句「X 和 Y 不能同时成立」）
- 版本：后台总览显示的 build SHA
- 建议：怎么修（可选）
```

**验收必须写版本。** 后台「运营指标」顶部会显示线上正在运行的 build SHA。验收记录写上它，才不会出现
「本地修好了，线上还是旧代码」，或者反过来。

## 一个改动的流程

1. **Claude 写规格**（`docs/*_SPEC.md`），末尾有「验收」一节。这一节就是 Codex 的检查清单。
2. **Claude 实现并开 PR。** PR 正文写清楚改了什么、怎么验证的。
3. **Codex 评审 PR。**
   - 看 diff，按规格的「验收」一节在本机走一遍。
   - 发现写成 PR 评论。
   - 没问题就评论「已评审，无发现」，写上评审的提交 SHA。
4. **Claude 处理评论，CI 通过后合并。** 合并就是上线（见 CLAUDE.md，「QA」就是生产环境）。
5. **Codex 线上验收**：用产品负责人的浏览器，按「验收」一节在 yuha.studio 上走一遍，并写上 build SHA。
6. **有问题回到第 1 步。** 先写规则，再修。

## 给 Codex 的入口

Codex 读仓库根目录的 `AGENTS.md`。那里指向这份说明和 CLAUDE.md。CLAUDE.md 里关于命名、运营者信息、
「验证要验证承诺本身，而不是验证页面画出来了」的规则，对 Codex 同样适用。
