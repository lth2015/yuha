# Claude 和 Codex 的协作说明

> 2026-10-30。YUHA 由两个 AI 代理一起开发：Claude（Claude Code，在云端容器里）和
> Codex（在产品负责人的电脑上）。两边互相看不到对方，只能通过仓库、PR 和产品负责人传话。
> 这份说明规定：谁做什么、结果放在哪里、用什么格式，好让一方的发现另一方马上就能处理。

## 分工

| | Claude | Codex |
| --- | --- | --- |
| 主要做 | 写规格、实现、测试，开 PR，合并后跟进部署 | 评审 PR，在线上做验收和安全测试 |
| 能接触到 | 仓库、CI、本地测试库、线上的公开页面和接口 | 产品负责人的浏览器和登录状态、线上后台、DGX |
| 碰不到 | 登录后的线上状态、真实支付、钱包、DGX | 这个云端会话 |

**两边都做逻辑检查。** 判断代码是否符合逻辑，不靠「看起来对」，而靠下面的「逻辑规则」。

## 逻辑规则：不能同时出现两个太阳

产品里有一些事情在任何时候都不能同时成立，就像白天不能有两个太阳、白天看不见星星。
这类规则要**写进代码**，由机器检查，不靠人记。

### 规则怎么写

- **代码在 `packages/db/src/invariants.ts`。** 每条规则是一个 SQL 查询，返回所有违反它的数据（只返回 ID）。查到 0 行才算通过。
- **每条规则都有反例测试**（`tests/invariants.test.ts`）：故意写进一行违反它的数据，确认检查能抓到，而且只抓到那一行。
  - 新增规则时如果没写反例，测试会失败。
  - 只有「通过」、没有「抓到过」的检查，可能根本什么都没在查。CLAUDE.md 里记过两次这种教训。
- **每个测试结束后自动检查全部规则**（`tests/helpers/invariant-guard.ts`）。
  - 任何一个测试只要留下违反规则的数据，就会失败，并写出违反的是哪条规则、哪一行。
  - 故意构造违规数据的测试，要用 `allowInvariantBreach('规则名')` 标注，并写一句为什么。
- **命令行**：`pnpm check:invariants [--json] [规则名…]`。
  - 连接方式和 `pnpm db:migrate` 一样：`DATABASE_URL`，或者挂载的凭据。
  - 只用一条连接，并设成 `READ ONLY`，所以可以对着生产库跑。
  - 有违反时退出码为 1。
- **后台**：「运营指标」的「逻辑规则」卡片显示生产数据上每条规则的违反数和示例 ID。
- 输出只有 ID，不含任何人的姓名或地址，可以直接贴进 PR。

### 第一次运行就抓到的

- `issue_reports` 和 `share_cards` 两张表一直没有在测试之间清空，上一个测试的数据会带进下一个。
  现在测试工具改为从数据库结构里读出全部表，再排除明确要保留的两张，不再靠人记清单。
- 「付了钱的订单有额度批次」第一版没有排除歌曲授权订单（授权订单发的是授权，不是额度），在
  `tests/market.test.ts` 上误报了 9 次。改成两条规则：额度订单有批次，授权订单有授权记录。

### 当前规则（16 条）

| 规则名 | 规则 | 为什么 |
| --- | --- | --- |
| `delivered-job-has-a-song` | 交付了的任务一定有作品 | 用户看到「完成」却找不到歌 |
| `delivered-job-spent-its-credit` | 交付了的任务一定已结算额度 | 否则额度一直被暂扣 |
| `failed-job-never-charged` | 失败、被拒、取消的任务从不扣额度 | 失败不收费（§6.1） |
| `ended-job-holds-no-credit` | 结束了的任务不再暂扣额度 | 额度不能悬在半空 |
| `credit-not-both-spent-and-returned` | 一个任务不能既「已使用」又「已退回」 | 同一份额度不能花两次 |
| `open-job-not-settled` | 进行中的任务还没有结算 | 结果没出来就不能下结论 |
| `finished-at-iff-ended` | 有结束时间，当且仅当任务已经结束 | 状态和时间要说同一件事 |
| `batch-counters-match-ledger` | 批次的计数和账本一致 | 账本是唯一真相 |
| `paid-order-granted` | 付了钱、标了已发放的额度订单，确实有它的额度批次 | 付钱才发货 |
| `paid-licence-order-has-its-licence` | 付了钱、标了已发放的授权订单，确实有它的授权记录 | 同上，对授权 |
| `unpaid-order-grants-nothing` | 没付钱的订单什么都没发 | 不付钱不发货 |
| `refunded-order-left-nothing-spendable` | 全额退款的订单没有留下还能用的额度 | 退了钱就收回没用的部分 |
| `song-belongs-to-its-maker` | 歌的主人就是生成它的人 | 不会把别人的歌算到你名下 |
| `report-status-matches-its-fields` | 已处理的报告有处理时间和说明；未处理的报告没有补偿 | 状态和内容一致 |
| `report-compensation-goes-to-its-owner` | 报告上的补偿批次属于报告的主人，来源是「补偿」 | 补偿不会发错人 |
| `job-compensation-points-at-its-job` | 绑在任务上的补偿，批次也指向同一个任务 | 每首歌最多补偿一次 |

**数据库本身已经保证、不需要查询的两条**：
- 批次的暂扣加已用不超过发放数（`CHECK` 约束）；
- 一个任务最多暂扣、使用、退回各一次（唯一键 `job_entry_uk`）。

### Codex 在逻辑规则上的分工

1. **评审规则本身。** 逐条读 `invariants.ts` 的 SQL，回答两个问题：
   - 会不会误报：有没有合法的数据也会被它抓到？
   - 会不会漏报：有没有违反这条规则、它却查不到的情况？

   结论写成 PR 评论。
2. **对生产库跑一遍。** 在产品负责人的电脑上，用生产库的只读连接执行 `pnpm check:invariants --json`。
   - 把结果贴进 PR 评论，附上后台显示的 build SHA。结果只含 ID，可以公开。
   - 有违反时，用 ID 在后台查清楚是怎么发生的：是规则写错了，还是真有缺陷。查到的细节如果含真实用户信息，只贴给产品负责人。
3. **提出新规则。** 验收中发现「这两件事不该同时成立」，按下面的报告格式写出来，并给出建议的 SQL。Claude 负责把它写进代码、加反例测试，然后修缺陷。

### 新规则从哪里来

**发现一个逻辑缺陷，先把它写成一条规则（或一个测试），再修。** 这样它以后再出现，检查会先发现。

- Codex 在验收中发现「这两件事不该同时成立」，在报告里用下面的格式写出规则。
- Claude 把规则写进代码，加上反例测试，再修缺陷。

## 结果放在哪里

| 内容 | 放在 | 原因 |
| --- | --- | --- |
| 代码缺陷、逻辑问题、建议（不含真实用户信息） | PR 评论，或 GitHub issue | Claude 订阅了自己开的 PR，评论一到就处理 |
| 含真实用户、订单、钱包、后台截图的内容 | 只留在本机，由产品负责人贴给 Claude | **仓库是公开的** |
| 安全漏洞的细节和复现 | 只留在本机，由产品负责人贴给 Claude | 修好之前不公开 |

运营者（yuha.studio 的经营者）本人的姓名、地址、电话和邮箱，不写进任何文件，包括 PR 评论
（见 CLAUDE.md 和 `pnpm check:stewardship`）。

## 报告格式

每条发现单独写，按严重度从高到低排：

```
[高 / 中 / 低] 一句话说明问题
- 现象：看到了什么（不含真实身份的复现步骤）
- 应该：本来应该怎样
- 违反的规则：（新规则就写一句「X 和 Y 不能同时成立」）
- 版本：后台总览显示的 build SHA
- 建议：怎么修（可选）
```

**验收必须写版本。** 后台「运营指标」顶部会显示线上正在运行的 build SHA。验收记录写上它，才不会出现
「本地修好了，线上还是旧代码」，或者反过来。

## 一个改动的流程

1. **Claude 写规格**（`docs/*_SPEC.md`），末尾有「验收」一节。这一节就是 Codex 的检查清单。
2. **Claude 实现并开 PR。** PR 正文写清楚改了什么、怎么验证的。
3. **Codex 评审 PR。**
   - 看 diff，按规格的「验收」一节在本机走一遍。
   - 发现写成 PR 评论。
   - 没问题就评论「已评审，无发现」，写上评审的提交 SHA。
4. **Claude 处理评论，CI 通过后合并。** 合并就是上线（见 CLAUDE.md，「QA」就是生产环境）。
5. **Codex 线上验收**：用产品负责人的浏览器，按「验收」一节在 yuha.studio 上走一遍，并写上 build SHA。
6. **有问题回到第 1 步。** 先写规则，再修。

Codex 读仓库根目录的 `AGENTS.md`。那里指向这份说明和 CLAUDE.md。CLAUDE.md 里关于命名、运营者信息、
