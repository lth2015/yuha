# YUHA 产品方向复盘：把做歌做好，让成品更容易分享

2026-11-26 · Codex 决策提案，供产品负责人与 Claude Code 独立评审。仓库基准 `064dad2`。本轮依据代码与负责人实际使用反馈，尚缺生产使用数据和新一轮试听基线。

## 建议决策

**下一迭代优先解决歌词与演唱的同步。把 MV 放在作品交付环节，保留 Veo 实验，暂缓扩大视频功能和推广承诺。**

**负责人补充的验收要求：自动歌词同步是有人声歌曲的基础体验。** 用户打开歌听，就应看到跟着演唱走的歌词。YUHA 在后台完成、验证并应用时间轴，用户无需进编辑器、拖每一行、试听逐行确认或点保存。波形和游标可以用来欣赏播放或编辑音轨。增加对齐成本可接受，目标是节省用户时间。具体模型和预算交给对照实验验证。

YUHA 的价值是「把想表达的感受做成一首完整的歌，听得清、唱得对、愿意分享」。照片 MV 与封面视频能帮用户把已经满意的歌发出去。Veo 可以增强这个出口，但它还没有证明比便宜的照片 MV 更能让用户分享歌曲。音质的提升来自负责人体验，歌词错位同样是实际反馈。两者的普遍程度都要用同一批样本量化。

### 视频做到哪里算合理

观看或生成一段视频并不会自动把 YUHA 变成视频平台。产品方向会变于三个地方：用户从视频开始而不做歌、团队主要时间消耗在视频、经营指标从满意的歌曲变成生成了多少视频。建议用以下边界管理：

| 环节 | 本轮取舍 | 判断依据 |
| --- | --- | --- |
| 首页、搜索、广告 | 核心承诺仍然是做歌，演示可用配有短片的完整歌曲片段 | 用户看到视频是为歌服务，首个行动仍是试做歌曲 |
| 歌曲页 | 自动同步直接在歌词区生效。照片 MV 和封面视频使用同一份可用时间轴 | 听歌、看歌词和导出都使用系统校准结果 |
| Veo 场景 MV | 保留规格、原型和适配器分支。后续实验以已有歌曲为前提，仅在独立预算内验证 720p 短片 | 评估能否让更多用户保存或分享这首歌，以及相对照片 MV 的增量成本 |
| 独立视频业务 | 本轮路线图内不安排视频首页、通用文生视频、素材库、视频社区或整首逐秒生成 | 这些会引入新获客、生成、计费、审核和售后链路，应有独立需求论证 |

三种选择里，砍掉全部 MV 会一起失去现有低成本传播能力；现在扩展 Veo 会在歌词质量尚不稳定时放大字幕问题，还要投入新队列与成本管理。保留照片／封面出口、给 Veo 留一个可撤回的实验，更适合现在的证据。若照片 MV 已能达到同等分享效果，Veo 留在实验即可；若 Veo 对分享有清晰增量，再单独决定价格、容量与公开范围。

### 拿什么决定下一次投入

- 音乐主指标建议用「首次做歌完成后 7 天内再次主动播放、下载／分享或再做一首的用户比例」，各行为同时单列，排除页面自动播放，区分试听与有意回访。同期跟踪歌唱歌词一致性、每首歌的端到端耗时、失败率。流量小时报告分子分母，别给小样本曲线过度解释。
- 视频实验按「符合条件的歌曲所有者」分组，让两组都能使用照片／封面，只对一组增加 Veo。比较每百名所有者的实际文件导出／发起系统分享与歌曲主行为是否变化，列出每多一次导出的增量成本和新增运营负担。打开分享面板不能当成已发布。先做小批内部可用性验证，有流量时再做带对照的增长实验。
- 原 Veo 预算与模式规格留作技术依据。若要上线或加大推广，先拿到模型实际扣费、视频处理区域和数据条款、真机保存结果及真实需求信号，再和歌词这条工作线比较机会成本。

## 歌词问题先分三类

| 听起来怎样 | 先检查什么 | 改善手段 |
| --- | --- | --- |
| 唱的是这句，但高亮早了、晚了或跳到另一次副歌 | 行与行出现次序、相同歌词不同出现位置、拖长音和间奏 | 人声时间戳＋段落匹配，取准确的起点和收尾。用带段落及出现次序的行标识区分重复副歌 |
| 歌声漏唱、改词、额外重复，或段落顺序真的变了 | 独立听写对比原稿。标注实际唱了什么、原词哪行缺失 | 系统自动区分可信对齐、疑似漏唱和无法确认的行。保留原稿与歌曲，不给未唱的行编造时间，也不擅自改词。写词长度与演唱执行偏差另做质量修复 |
| 对齐结果本身准，页面或导出仍偏移 | 播放和导出是否使用同一音轨版本、选段起点、跳播、重新编码后的时间基准 | 修复时间轴映射或版本问题，复用相同的媒体时间源。给同一段音频做起播、拖动和成片试听对照 |

**愿意为准确度付费，值得做。** 建议付费买带时间戳的音频证据，再让模型处理结构歧义。优先比较对歌声有实证的 ASR 或专用对齐服务；音频大模型可以参与识别含混片段，但需提交有时间范围的音频证据，并按同一标准打分。纯文本大模型适合匹配副歌、读音和段落，单凭歌词猜秒数没有音频证据。即使歌词模型写得更好，也无法补回成品里已经漏唱的句子。

## 第一轮实验怎么做

1. **建立基准。** 复用六首中日英固定测试歌的已有授权音频，补齐到建议首轮 18 首（各语言六首），覆盖短句、长前奏／间奏、重复副歌、缺词／换词、拖长音、中日语言混用及低信心段落。先复用资产，缺样本再安排生成。保留 6 首不参与调参。样本是原创、合成或确认获准使用的音频。只交换脱敏统计。
2. **两人盲听标注。** 同一文件标注每行实际出现次序、第一可辨唱字起点、末尾唱字、未唱／额外行。遇到不清楚的内容标「不确定」，列出分歧和裁定记录。保留两人可接受误差，避免用单人的主观拍点做毫秒级绝对标准。
3. **按同一音频比较三条路线。** A 为现有 DGX 及回退的真实输出。B 复用可用的人声 stem，用带词或片段时间戳的语音／对齐服务做独立证据，再与原词匹配。C 在 B 的重复副歌、漏唱、低信心段内，用可听音频的模型或基于时间戳的文本模型做局部判别。先判断 B 是否足够，再算 C 的增量。先对少量授权样本验证是否适合歌声和中日英，书面记录价格、数据处理区域、训练、留存及音频长度限制，再使用实际凭据和预算。
4. **按失败吃亏的方式算分。** 起点绝对误差报中位数与 P90，另列 ±300 ms 命中率、超过 1 秒的严重错位率、唱到却无可用时间戳的比例、未唱却高亮和重复段错配率。以人工确认唱到的行作命中率分母，超时、空结果及漏行计作未命中；未唱却高亮单独计分。按中日英、常规与疑难分组报告，同时记录每首处理时延、全部请求成本和被接受修正的成本。18 首仅供发现差异，P90 与语言分组都要带样本数。
5. **分别判断候选是否更好、自动交付是否达标。** 采纳 Claude 的建议，按同一行配对并按歌曲估算不确定区间，结合标注者分歧解读 ±300 ms 命中率。样本太少就扩样。未唱却高亮增加时不采用候选。还要报告整首歌自动可用率、首播就绪率和每种语言的实际覆盖，避免靠隐藏很多行提高命中率。请 Claude 根据基线提出绝对验收线和超时目标。只改善逐行分数或状态标签，不能算完成自动交付。试听和标注由测试人员负责。

**付费调用顺序。** 先修已知缺陷并建立基准，同时准备一条带音频时间证据的付费对照。修完以后，准确度、首播就绪率或失败恢复仍未达标时，按确认额度用授权样本做对照。Claude 提议单次小试上限 $5，作为预算建议。只给低信心段加算是候选策略。若全曲付费路径经实测更稳、耗时和成本可接受，也可以考虑默认使用。记录 `每 1,000 首额外成本 = 1,000 × 付费触发比例 × 触发后平均实际成本`，后者含失败与重试。当前建议由平台承担对齐成本，付费模型属于成品质量投入。这轮评审未产生付费调用。

## 下一迭代的交付边界

- **接续 Claude 的评审。** L1 修复迟到结果覆盖已有校准。L2 让系统识别低信心行并触发有界自动补救。L3 建基准。L4 改为自动开始、自动应用及歌词区状态反馈。L5 在基准显示需要更多音频证据或更稳定的服务时比较付费候选。L1–L3 是必要工程步骤，完成自动交付看 L4 的端到端结果。 [Claude 独立评审 #147](https://github.com/lth2015/yuha/pull/147)
- **新歌首次播放。** 成品音频可用即自动对齐，尽早在首次播放前准备好结果。对齐未完成时歌曲可先听，歌词区显示「正在同步」。验证通过的结果自动应用、刷新后仍生效。版本要和实际交付音频及歌词对应，迟到任务不得覆盖已有人工版本或新音频、歌词版本。
- **低信心或失败。** 系统用有容量和时限的重试／候选回退自行处理，给长期失败明确状态。必要时允许用户点一次「重新自动同步」，后台完成后直接生效。疑问行保留可读原词，跳过该行的实时高亮和默认字幕。暂时无法确认整首时，提供静态歌词和无字幕导出。失败后的降级仍计入自动同步未完成。
- **已经做好的歌。** 对缺失、估算或有质量疑问的旧时间轴，按用户打开有问题的歌或选定批次触发重新自动对齐，避免全库无差别重跑。优先从已交付音频取源，并保留已有可信版本，具体排期、限额与回退由 Claude 说明。
- **交叉验收。** 新歌和需要重算的旧歌分别验收。用户仅打开和播放，验证系统自动产出、应用和恢复同步。用中日英样本从头听、拖播放进度、切重复副歌，并导出同一段字幕视频。另测超时、漏唱、重复提交和版本竞争。统计在零人工操作下整首实际可用的比例、每种语言的失败率以及音频就绪至同步可用的耗时。波形、游标和音轨编辑按体验价值单独验收。
- Veo 的 adapter、原型和技术验证结果保留，建议本轮排在歌词之后。下一次做视频方向决定时，把音频一致性、对齐体验、真实分享增量和单位成本放在一张表比较。
