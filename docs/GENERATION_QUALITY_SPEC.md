# 重新定义「生成成功」— 规格

> 2026-10-30。路线图第三项：「应分别记录：任务完成率、音频可播放率、完整交付率和用户认可度。
> 生成接口返回成功，不能代表没有漏唱、歌词错位或音质问题。」以及第五项里的「历史累计成功率与
> 当前版本表现应分开，否则很容易误判修复效果」。

## 现在的问题

后台只有一个数字：**技术成功率**，即最近 7 天交付数除以结束数。

- 一首歌只要引擎返回了音频就算成功，哪怕：
  - 短了一半；
  - 歌词时间轴退回了估算（没对上）；
  - 用户听完就删了，或者报告了漏唱。
- 修复上线后，这个数字仍然混着修复前的任务，看不出修复有没有效果。

## 四个数字

统计最近 24 小时和最近 7 天内**结束**的任务。用户自己取消的不计入，因为那不是生成的成败。

| 指标 | 分子 | 分母 | 说明 |
| --- | --- | --- | --- |
| 任务完成率 | 交付的任务 | 交付 + 失败 + 被拒 | 引擎层面的成败 |
| 音频可播放率 | 有主音频文件，且大小和时长都大于 0 | 交付的任务 | 交付了，但文件坏了也算失败 |
| 完整交付率 | 时长达标（≥ 要求的 90%），并且有人声的歌的歌词时间轴不是「估算」 | 交付的任务 | 短歌、截断、歌词没对上都算不完整 |
| 用户认可度 | 交付满 24 小时后仍然保留、没有被报告问题的歌 | 交付满 24 小时的歌 | 用户用行动表达的认可 |

完整交付率下面再拆两个数，方便定位问题出在哪一环：

- **时长达标率**：交付时长 ≥ 要求时长的 90%；
- **歌词对齐率**：只看有人声的歌，时间轴来源是「对齐」或「手动校正」。

## 按版本分开

- 每个任务创建时记下当时 API 的 build SHA（新增列 `generation_jobs.build_sha`，迁移 0029）。
- 后台把四个数字分成两列显示：**当前版本**（等于正在运行的 build SHA）和**全部**。
- 迁移之前的任务没有 SHA，只算进「全部」。
- 当前版本的样本少于 10 个时，照常显示数字，同时标出样本数，不让人把 3 个样本当成趋势。

## 能追到具体任务

每个指标显示最近未达标的任务 ID（最多 5 个），点进后台客户页就能看到这个任务。
ID 只是 ID，不含个人信息。

## 不做的事

- 这一项不做「固定测试歌词定期检查」。它需要在生产环境用真实额度生成，还要有人去听，所以作为下一项单独做，交给 Codex 和产品负责人执行（见协作说明）。
- 不改「技术成功率」这个旧数字，保留它，避免已有的看法突然失去参照。

## 验收

- 四个指标和两个拆分指标的分子分母都有测试：用真实的生成流程构造各种情况，包括短歌、估算时间轴、删歌、被报告问题，以及用户取消（不计入）。
- 当前版本和全部分开计算；没有 SHA 的旧任务只进「全部」。
- 未达标示例的 ID 能在后台对上。
- 三种语言，360 / 393 / 768 / 1280 宽度（`pnpm check:ui`）。
