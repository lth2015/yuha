# YUHA · 为别人写一首 ＋ 分享卡片 — 规格

> 2026-10-28。状态：三部分都已实现（第三部分按用户「都做了吧」一并实现）。
> 起因：演示时大家觉得惊艳，但写完两首就没有理由再回来。最自然的回来理由，
> 是「有个人值得一首歌」；最自然的拉新，是那个人收到了一首歌。

## 现状（读代码得到的事实）

- 歌曲页已有「分享」菜单（`components/ShareMenu.tsx`）：复制链接、X / LINE /
  Facebook / 微博的发帖链接、手机自带的分享面板。只有公开的歌才显示。
- **链接预览是全站同一张**：`apps/web/index.html` 里只有固定的 `og:title` /
  `og:description`，**没有 `og:image`**。所以发到 X 的任何一首歌，预览都是
  「YUHA — 让心动，有回声。」，没有图，看不出是哪首歌。
- 生产环境的网页在 S3 + CloudFront 上，CloudFront 只有 S3 一个源。X 的抓取器
  不执行 JavaScript，所以 `yuha.studio/song/…` 不可能按歌给出不同的预览，
  除非 SRE 改 CloudFront。API 在自己的域名（`PUBLIC_API_URL`）上。
- 没有视频导出。现在能下载的只有 mp3 / wav。
- 「公开」的意思是拿到链接的人能打开；没有广场、没有点赞、没有播放数给人看
  （CLAUDE.md 的范围决定）。这里的一切都守这条。

## 第一部分：为别人写一首

### 创作时

`/create` 加一个可选的「送给一个人」：

| 字段 | 规则 |
| --- | --- |
| 送给（名字或称呼） | 必填（选了送人时），≤ 20 字 |
| 场合 | 生日 / 谢谢你 / 对不起 / 喜欢你 / 想你 / 再见 / 加油 / 其他 |
| 想对 TA 说的一句话 | 可选，≤ 120 字 |

- 名字和场合会写进给模型的提示里，所以 AI 写的歌词本身就是为这个人写的。歌词
  如果是自己写的，就照原样唱，提示里也会这样说清楚。
- 这句话会公开给拿到链接的人看，所以和提示词一样过内容检查
  （`checkPrompt`），被拦的话说明原因，不扣额度。
- 首页的简单路径不变，「送给一个人」只在 `/create` 里，因为它需要多填两样。

### 存储

迁移 0026：`tracks.dedication JSON NULL` = `{ to, occasion, note }`。
没有送人的歌是 `NULL`，行为与现在完全一样。

### 歌曲页

- 有赠言的歌，页面顶部是赠言：「给 小林 · 生日快乐」＋ 那句话，然后是播放。
- 主人看到的主按钮变成 **「送给 TA」**：
  1. 如果歌还是私密的，先说清楚「送出后，拿到链接的人都能听」，确认后设为公开；
  2. 打开分享菜单，文案按场合写好，例如「我为你写了一首歌：《…》」。
- 收到的人（没登录也行）看到的是：赠言、大播放键、歌词，最下面一行
  **「我也给一个人写一首」** → 登录 / 注册 → `/create`（送人已打开）。
  新账号照常拿免费试用额度，这里不另外送。

### 不做的事（以及为什么）

- **送出的歌不上首页展示**。「公开」对一首送人的歌，意思是收到链接的人能打开，
  不是让每个来首页的人看到 TA 的名字和那句话。首页列表排除有赠言的歌，列表里的
  视图也不带赠言（代码审查发现，`tests/gift-and-share.test.ts` 钉住）。
- 删除一首歌时，赠言和预览卡片一起删除，不等到注销账号。

- **不告诉送歌的人「TA 听了」**。已读回执就是一个计数器，而且把一份礼物变成
  一次考核。运营侧会记录 `gift_opened`（只进分析表，不给任何用户看）。
- 不做「收到的歌」列表。收到的人没有账号也能听，那首歌属于写它的人。

## 第二部分：分享卡片（链接预览）

1. **全站补一张预览图**：`/brand/og-card.png`（1200×630），加到
   `index.html` 的 `og:image` / `twitter:card=summary_large_image`。从此任何
   YUHA 链接发出去都有图。
2. **按歌的卡片**：分享菜单里的链接改成
   `${PUBLIC_API_URL}/v1/share/songs/:id`。这个地址返回一页很小的 HTML：
   - 公开的歌：`og:title` 是歌名（有赠言时是「给 小林 的一首歌」），
     `og:description` 是场合或风格，图是上面那张；然后立即跳到
     `yuha.studio/song/:id`。
   - 私密、删除或不存在的歌：不带任何歌的信息，直接跳到歌曲页（由歌曲页照常
     说「不存在或不公开」）。歌名不会通过预览泄露。
   - 跳转目标只能是 `PUBLIC_WEB_URL` 下的 `/song/:id`，用 `new URL` 拼并核对
     origin（CLAUDE.md：拼接不是构造 URL）。
3. **验证方式**：上线后用 X 抓取器的 User-Agent（`Twitterbot`）请求那个地址，
   核对返回的 meta；再真发一条到 X 看卡片。
4. 以后如果 SRE 给 CloudFront 加一条 `/song/*` 到 API 的规则，就能直接用
   `yuha.studio/song/:id`，这一层可以去掉。不在本次范围内。

每首歌自己的封面图（把歌的「乐谱」画成 PNG）需要服务端画图，先用统一的图，
看第三部分一起决定。

## 第三部分：分享视频

X、Instagram、TikTok 上真正会被点开的是视频，不是链接。设想：15–30 秒竖版
MP4——封面「乐谱」在动、歌词随声音亮起、配上这首歌最好的一段——由 worker 用
ffmpeg 渲染，在手机上通过系统分享面板作为文件直接发出去。

实现方式（为什么这样分工）：

- **浏览器画帧**：`apps/web/src/lib/share-art.ts`。封面、歌名、「写给 谁 · 场合」、
  每句歌词各一帧，720×1280 JPEG。字体、封面颜色只有浏览器有。中文文字优先用中文
  字体：M PLUS 2 有「那年夏天」却没有「谢」，同一行会混两种字重。
- **选段**：`planShareClip`——有标注的副歌就从副歌前 1.5 秒开始，否则从第一句前，
  纯音乐从四分之一处；20 秒，不超出歌的结尾。
- **服务器合成**：`POST /v1/tracks/:id/share-video`（仅本人）。ffmpeg 把帧按歌词
  时间接起来，配上这首歌自己的音频，加一条随音乐动的波形，返回 MP4。**不存储**。
  每个 API 进程同时只做一个（第二个请求得到 429），50 秒硬上限，`/tmp` 是 emptyDir。
- **两次点击**：手机只允许在点击后几秒内打开分享面板，而做视频要几秒，所以先
  「制作分享视频」，好了再「发送视频」。不支持文件分享的桌面浏览器改为下载。

## 之后（另写规格）

- 心情日历：「我的歌」按日期排成日历，只给自己看。
- 温柔的回访邮件：「一年前的今天你写了这首歌」；额度重置时「你的 5 首准备好了」。

## 上线后验证（只有生产环境能证明的）

1. 链接预览走的是 API，不是被 CloudFront 当成网页返回（CLAUDE.md：未转发的路径会
   200 返回 SPA）：
   `curl -s -A 'Twitterbot/1.0' https://yuha.studio/v1/share/songs/<公开歌曲id> | grep og:title`
   必须看到歌名；看到「YUHA — 让心动，有回声。」和一整页 HTML 就是路由没通。
2. 普通浏览器打开同一地址 → 302 到 `/song/<id>`。
3. 真发一条到 X（或用 LINE 发给自己），看卡片是否是这首歌的图。
4. 手机上「制作分享视频」→「发送视频」能弹出系统分享面板。

## 验收

- 送人的歌：创作 → 歌词里出现了名字或场合 → 页面显示赠言 → 「送给 TA」把私密
  歌先确认再公开 → 分享文案正确。三种语言，360 / 390 / 768 / 1280 宽
  （`pnpm check:ui`）。
- 没登录的人打开链接：能听、能看歌词、看到「我也给一个人写一首」，点了能一路走到
  `/create` 且送人已打开。
- 卡片：公开的歌返回歌名和图；私密的歌返回的 HTML 里找不到歌名；跳转目标被构造
  成别的域名时拒绝。
- 不出现任何给用户看的计数。
